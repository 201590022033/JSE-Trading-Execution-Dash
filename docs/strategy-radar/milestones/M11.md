# Strategy Radar M11 - data freshness and prepared research context

Status: COMPLETED LOCALLY AND LIVE-VERIFIED - 12 November 2026. Research M5
remains active and unchanged; this is a separate, owner-authorized Strategy
Radar milestone.

## Context

The owner asked for visible source freshness and logically linked refresh or
manual-import actions across the dashboard, plus local research context that is
ready when a Backtest investigation is started. Existing sources have different
clocks and different refresh paths. A missing expiry rule must not be replaced
with a fabricated deadline, and a freshness read must not start a provider or
model job.

## Scope and boundaries

- A local-only `/api/v1/data-freshness` read combines existing Zebra daily
  coverage, manual quotes, imported intraday bars, news/SENS, saved backtests,
  strategy profiles, OST/ViewPoint import receipts, local paper state and
  browser-session visibility.
- The browser refreshes this local status snapshot at most once per minute while
  visible and renders source-specific countdowns locally. Buttons route to
  existing explicit refresh/import actions or open the source for user-operated
  access. OST/ViewPoint sign-in status and timeout remain unknown; no keepalive,
  login automation or session polling is introduced.
- A retained local context packet is refreshed after Top-5 membership changes,
  manual selections/pin changes, successful ViewPoint CSV import, completed
  retained news capture, and the existing SENS/calendar tick. Existing watches
  receive one baseline packet on the first local service initialization. It includes at
  most six current choices, 150 merged intraday bars per choice, 20 news items,
  20 SENS items, and 20 calendar entries. An imported instrument outside the
  six radar choices is included only in a separate import-evidence section.
- Packets are local SQLite snapshots, retain source clocks and lineage, and
  keep the latest 100 snapshots. Preparation reads existing caches and retained
  records only; it performs zero provider calls, model calls, backtest runs, or
  broker actions. It does not create forecasts or trade signals.

## Acceptance and verification

1. Each dashboard area exposes its applicable freshness clocks and a nearby
   action; manual sign-in displays no invented timeout.
2. The freshness endpoint is loopback-only and cache/read-only. Unit coverage
   verifies that status checks do not schedule news scans.
3. Prepared context respects its choice and evidence bounds and is triggered by
   Top-5, pin, ViewPoint import, news, and SENS/calendar updates.
4. Focused Python tests, JavaScript syntax, endpoint checks, and whitespace
   validation pass. Browser viewport measurement reports no horizontal
   overflow at a 390px setting (375px document width).

Focused validation passed 87 tests across context, freshness, feeds, intraday,
Radar and anticipatory-radar modules; JavaScript syntax checks and
`git diff --check` passed. A real Flask test client returned HTTP 200 with all
eight area groups and no retained-database errors. After a normal dashboard
restart, the live freshness endpoint returned AVAILABLE with eight areas and
no endpoint errors; the dashboard displayed the freshness rows and PREPARED
Radar context. The 390px viewport had no horizontal overflow.

The first persisted packet contains five current choices, all with daily
history through 11 November, eight retained five-minute MTN bars, 20 SENS
leads, and eight calendar events. No five-minute bars were retained for the
other four choices; the in-memory news cache was not loaded at capture time.
The packet prepares available context but does not automatically download
missing bars. These are source-coverage follow-ups, not failures of M11's local
preparation or freshness-display contract. Exact OST/ViewPoint browser idle
timeouts and the earlier Save-button pause remain unresolved.
